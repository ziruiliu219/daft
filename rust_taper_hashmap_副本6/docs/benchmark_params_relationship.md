# Benchmark 参数关系图

## 三个参数的关系

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  ht_size = 1024 (hash table 总 slot 数)                              │
│      │                                                               │
│      │  × load_factor = 0.5                                          │
│      ▼                                                               │
│  num_keys = 512 (build 阶段放入的 unique key 数)                      │
│      │                                                               │
│      │                                                               │
│      ▼                                                               │
│  ┌────────────────────────────────────────────────┐                  │
│  │ Hash Table (1024 slots)                         │                  │
│  │                                                │                  │
│  │  [key][key][ ][ ][key][ ][key][ ][ ][key]...   │                  │
│  │   ↑    ↑         ↑       ↑         ↑          │                  │
│  │   512 个 slot 被占用, 512 个空着                 │                  │
│  └────────────────────────────────────────────────┘                  │
│                     │                                                │
│                     │  然后 1M probe rows 来查这张表                    │
│                     ▼                                                │
│  num_probe_rows = 1,000,000                                          │
│      │                                                               │
│      │  × selectivity = 0.7                                          │
│      ▼                                                               │
│  num_hits = 700,000 (key 存在于表中, probe 命中)                       │
│  num_misses = 300,000 (key 不在表中, 要创建新 group)                   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

---

## 具体例子: ht_size=1024, lf=0.5, sel=0.7

### Phase 1: Build (创建 512 个 group)

```
build_a = [1, 98, 195, ..., 49665]     ← 512 个确定的 key 值
build_b = [7, 60, 113, ..., 27079]

Hash Table 状态:
┌─────────────────────────────────────────────────┐
│ 1024 个 slot 中:                                 │
│   512 个被占用 (存了 512 个 unique group)          │
│   512 个空着                                     │
│   load factor = 512/1024 = 0.5                   │
└─────────────────────────────────────────────────┘
```

### Phase 2: Probe (100 万行查表)

```
100 万行来查这张表:

  700,000 行 (hit): key = 从 512 个 build key 里随机选
    → 能在表里找到 → 更新 sum
    → 例: row 想找 (98, 60) → hash table 里有 → sums[gid] += val

  300,000 行 (miss): key = 全新的、不在表里的值
    → 找不到 → 创建新 group → 表变更满
    → 例: row 想找 (99999, 88888) → 不在 → 插入新 slot

最终 Hash Table:
┌─────────────────────────────────────────────────┐
│ 1024 + 扩容后的 slot 中:                          │
│   512 + 300,000 = 300,512 个 group               │
│   (table 会自动扩容多次)                           │
└─────────────────────────────────────────────────┘
```

## 每个参数影响什么

```
                    ┌─────────────┐
                    │  ht_size    │ = hash table 初始大小
                    │  256/1024/  │
                    │  4096/16384 │
                    └──────┬──────┘
                           │ 决定
                           ▼
              ┌────────────────────────┐
              │ 表有多大 (内存 / cache) │
              │ 小表: L1 cache 放得下   │
              │ 大表: L2/L3 才放得下    │
              └────────────────────────┘


                    ┌─────────────┐
                    │ load_factor │ = build 后表有多满
                    │  0.5 / 0.75 │
                    └──────┬──────┘
                           │ 决定
                           ▼
              ┌────────────────────────┐
              │ probe 时碰撞多不多      │
              │ lf=0.5: 空位多, 少碰撞  │
              │ lf=0.75: 较满, 多碰撞   │
              └────────────────────────┘


                    ┌─────────────┐
                    │ selectivity │ = probe 行有多少能命中
                    │ 0.1~0.9    │
                    └──────┬──────┘
                           │ 决定
                           ▼
              ┌────────────────────────┐
              │ comparator 被调多少次    │
              │ sel=0.9: 90% hit → 大量 │
              │ sel=0.1: 10% hit → 很少 │
              └────────────────────────┘
```

---

## 为什么要测这三个维度

| 参数 | 测什么 | 对 Taper 有利的情况 |
|------|--------|-------------------|
| ht_size | 表大小对 cache 的影响 | 大表时 chunk 128B 对齐可能更友好 |
| load_factor | 碰撞率的影响 | 高碰撞时 SWAR tag 预过滤更有价值 |
| selectivity | comparator 调用频率 | 高 selectivity (多 hit) 时 deferred compare 省得多 |

---

## 组合示意

```
ht=256,  lf=0.5, sel=0.9 → 小表、半空、90% hit  → 最快场景
ht=16384, lf=0.75, sel=0.1 → 大表、七成满、10% hit → 最慢场景 (大量 miss + 碰撞)

benchmark 遍历所有组合:
  ht_size   ∈ {256, 1024, 4096, 16384}
  lf        ∈ {0.5, 0.75}
  sel       ∈ {0.1, 0.3, 0.5, 0.7, 0.9}

  = 4 × 2 × 5 = 40 组测试
  每组: daft vs taper
  总共 80 个 benchmark 点
```

## 数据流时间线

```
时间 →

0                              512 行                              1,000,512 行
├─────── Build ────────────────┤──────────── Probe (1M 行) ────────────────────┤
│ 创建 512 个 group            │ 700K hit (更新 sum)                            │
│ 表从空 → 50% 满              │ 300K miss (创建新 group, 表越来越满)            │
│ 无碰撞 (全是新 key)          │ 有碰撞 (hit 要 probe 找到正确 slot)            │
└──────────────────────────────┴───────────────────────────────────────────────┘

                                ↑ benchmark 测的主要是这段 (1M 行)
                                  因为 build 只有 512 行, 占比很小
```
